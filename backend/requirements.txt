# ── pydantic / pydantic-settings: RANGES, measured 2026-10-10 ──────────────────
#
# These were `==2.9.2` and `==2.5.2`, and on the Python 3.14 cabinet they were
# UNINSTALLABLE. pydantic 2.9.2 needs pydantic-core 2.23.x, which ships no cp314 wheel, so
# pip fell back to a source build: maturin -> PyO3 0.22.2 -> "the configured Python
# interpreter version (3.14) is newer than PyO3's maximum supported version (3.13)".
#
# AND PIP RESOLVES THIS FILE ATOMICALLY. One unbuildable package aborts the whole
# `pip install -r requirements.txt` before anything is installed — proven on cabinet 1 on
# 2026-10-10, where `pip freeze` before and after the failed install was byte-identical.
# So this pin was not merely wrong about pydantic: it blocked EVERY package in this file
# from ever installing, on every upgrade, since the 3.14 venv was hand-built on
# 2026-06-13. `reportlab` was the visible casualty — declared here and absent from
# production for four months.
#
# THE TRADE-OFF, STATED RATHER THAN HIDDEN. A range costs reproducibility: two cabinets
# can resolve to different versions. But a pin that cannot install gives no
# reproducibility at all, only a failed install and whatever happened to be there — which
# is strictly worse, because it also looks like nothing happened. A range that resolves
# beats a pin that does not.
#
# AND REPRODUCIBILITY IS NOT THIS FILE'S JOB. This file declares what our code is
# COMPATIBLE with. What was actually INSTALLED belongs in a lockfile. PEP 508 markers
# (`pydantic==X; python_version < "3.14"`) try to do the lockfile's job here and do it
# badly: two lines per package, and a new branch every time an interpreter joins the
# fleet. When we want reproducibility the answer is a constraints file generated from
# `pip freeze` per cabinet, kept next to that cabinet — not branches in here.
#
# Lower bounds are the versions the Ubuntu 24.04 / Python 3.12 cabinet runs, so that
# machine keeps working. Upper bounds are the next major, where these two break
# compatibility on purpose.
#
# VERIFIED 2026-10-11, full backend suite on the dev box, three points across the range:
#   pydantic 2.9.2  + pydantic-settings 2.5.2   (the old pin, = the 24.04 cabinet)
#   pydantic 2.12.5 + pydantic-settings 2.5.2
#   pydantic 2.13.4 + pydantic-settings 2.14.1  (= cabinet 1 today)
# 1030 passed, 34 skipped on all three, identical.
#
# CONFIRMED ON CABINET 1 (MAR_KRK_ORM_01), 2026-10-11 10:31 local. `pip install -r` ran to
# completion with no error for the FIRST TIME SINCE 2026-06-13 — zero hits for "ERROR:
# Failed building", "error: failed-wheel-build" and "pip install had errors". pip freeze
# gained exactly two entries, both accounted for: reportlab==4.2.5 and chardet==7.6.0
# (reportlab's own dependency — `pip show chardet` reports Required-by: reportlab).
# openapi.json returned 200 afterwards.
#
# A CHANGED venv is the proof here. The night before, an UNCHANGED venv was the proof —
# that the failed install had touched nothing. Same check, opposite sign, and which one
# applies depends on what is being proved. See docs/engineering_notes.md.
pydantic>=2.9,<3
